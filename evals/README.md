# Evals AgentDispatch

Эти два прогона измеряют разные свойства маршрутизации. `routing` проверяет, насколько живой роутер выбирает ожидаемый executor на размеченных coding-задачах. `smoke` отправляет реальные задачи в живой daemon и проверяет результат в изолированной временной Git-репозитории.

Запуск:

```bash
uv run python -m evals.routing
uv run python -m evals.routing --router claude_local
uv run python -m evals.smoke --executors omp
```

По умолчанию `routing` использует живой daemon. Режимы `--router jev` и
`--router claude_local` работают in-process, обходят daemon и предназначены для
сравнения бэкендов маршрутизации.

`replay` бесплатный и детерминированный: читает живую `dispatch.db` и считает, что правила диспатчера изменили бы на прошлых задачах.

```bash
uv run python -m evals.replay            # сводка
uv run python -m evals.replay --json     # полный отчёт
uv run python -m evals.replay --cooldown 1800
uv run python -m evals.replay --since 2026-10-01 --accept-window-hours 24
uv run python -m evals.replay --no-git --baseline-tier strong
```

Что меряет `replay`: сбои исполнителя и сколько запусков ушло бы к уже остывающему (лимит держится до объявленного сброса на всю группу лимита, `limit_reset` и группы берутся из конфига), удержание интеграции перед эскалацией, `partial` из-за формата отчёта и задачи на правку, отданные исполнителю «только для ревью» (`routing.review_only`). Ложное срабатывание остывания видно как запуск со статусом `completed` в `avoidable_runs`: такого быть не должно.

|---|---:|---:|---:|---:|---:|
| 2026-09-30 (остывание 900 с) | 120 | | 7 (180 мин) | | |
| 2026-10-03 до правки лимитов | 171 | 15 | 9 (188 мин) | | |
| 2026-10-03 сброс по сообщению, группы | 171 | 31 | 24 (190 мин) | 0 | 50 запусков, 21 упал, 208 мин |

До правки 14 отказов `claude/opus` по недельному лимиту 2 октября не распознавались вовсе (`hit your weekly limit`). Первая версия правки дала 8 ложных блокировок: лимит расходов, поднятый человеком через 7.5 часа после «resets Sep 26», и балансер лимитов, который отдал свободный аккаунт раньше названного «Try again at 5:02 PM». Отсюда перепроверка лимита расходов и `limit_reset: recheck`.

Секции ниже отвечают на вопрос, есть ли от делегирования толк:

- `perimeter_violations`: запуски внешних исполнителей при обязательном корпоративном периметре; порог 0. Требование берётся из `request_json.prod`, `decision.meta.perimeter` (`prod`, `answered`, `unknown`) и предков по `escalated_from`, `followup_of`, `parent_task_id`. `prod` сильнее остальных меток, отказы guard'а нарушениями не считаются. Признак корпоративного исполнителя берётся из текущего конфига, поэтому его изменение может дать ложное срабатывание на истории.
- `prod`: число задач всей prod-линии, включая ревью, незавершённые задачи и отказы до записи решения роутера (`tasks`); распределение запусков по исполнителям без отказов guard'а (`executors`); вердикты автоматического ревью из `result.meta.review` (`review_verdicts`: `pass`, `fail`, `unknown`, `skipped`). Отсутствие ревью не считается `unknown`. В `redacted` число результатов с очисткой (`tasks`), сумма замен (`replacements`) и число очищенных результатов по полям (`fields`), без самих секретов. Нулевое число очисток не доказывает отсутствие утечки: маскируются только известные формы секретов в `summary` и `error`. `load` восстанавливает унаследованный `prod` до фильтра `--since`, поэтому предок вне окна не скрывает продового потомка; в счётчики входят только задачи внутри окна.
- `children_refusals`: прошлые отказы `max_children`, пересчитанные по сегодняшнему правилу `Storage.count_children`: квоту занимают только назначенные, не отменённые дети без ретраев эскалации, а сама задача и отказанные попытки не в счёт. Из отказов одного родителя допускается не больше, чем осталось свободных мест, остальное считается ретраями отказа.
- `delegations`: исходная задача вместе с цепочкой эскалаций. Если в цепочке нет ни `completed`, ни изменённых файлов, делегирование `wasted`. Причина берётся у последнего звена: `guard`, `cancelled`, вид сбоя исполнителя из `health.py`, `timeout`, `no_report`, `task_failed`. Задачи из `queued`/`running` идут в `in_flight` и не судятся.
- `acceptance`: диф дошёл до рабочей копии (`integrated` не `false`), после чего за `--accept-window-hours` (по умолчанию 48) вызывающий закоммитил хотя бы один из `changed_files`. Служебные коммиты демона `agent-dispatch: task …` не считаются. Коммит сам по себе это верхняя оценка, поэтому для дифов с сохранённым патчем (`meta.patch`) считается ещё доля значимых добавленных строк (от 8 символов), которые есть в файле на первом коммите вызывающего: `kept` от 80%, `reworked` от 20%, иначе `rewritten`. Если `cwd` удалён (вызывающий убрал свой feature-worktree после слияния), коммит ищется в общем git dir по всем веткам, кроме stash: сначала записанный демоном при `submit` (событие `git` задачи: `common_dir`, `branch`), у старых задач ближайший живой предок `cwd`, если он сам в git, иначе git-checkouts среди его прямых детей, если у всех один общий git dir. Где судили, видно в `judged_via` (`cwd`, `recorded`, `ancestor`, `siblings`). Остальное `unknown` с причиной в `unknown_by_reason`: `cwd_gone` (каталога нет, репа не нашлась), `ambiguous` (соседи из разных реп), `not_git` (каталог есть, но не git: обычно остаток удалённого worktree с `.idea`; ищется так же, как удалённый), `git_error`. Догадка по предку или соседям засчитывается, только если в истории найденной репы есть хотя бы один из `changed_files`; иначе `unverified_repo`: так посторонняя репа над `cwd` (например, домашний каталог под git) не судит чужой диф. Файл, который знает только stash, тоже даёт `unverified_repo`. `--no-git` выключает секцию.
- `timeouts`: жёсткие таймауты (`error: timeout`) по исполнителям со средней длительностью. `active` — CLI писал в stdout/stderr за 120 с до убийства (`meta.last_output_age_s`): агент работал до конца, этому исполнителю мал таймаут (`executors.<имя>.timeout_seconds`) или задачу надо дробить. `quiet` — молчал дольше, агент висел или ждал. `no_stream` — CLI печатает всё в конце (claude), молчание ничего не значит. `unknown` — задачи до появления поля.
- `cost_drift`: `usage.cost_usd` задачи против учёта agent-lb (`request_logs` в `--agent-lb-db`, по умолчанию `~/.agent-lb/store.db`, только чтение) для той же сессии: omp и claude передают балансеру id своей сессии, тот же, что в `result.meta.session_id`. Потолки бюджета верят самоотчёту CLI, а CLI считает по своему каталогу цен, балансер по своему `pricing.py`. `ratio` — доля счёта, которую увидел бюджет; задача с расхождением больше 10% попадает в список и в рекомендации. Сессии сабагентов omp у балансера отдельные, их нет ни в самоотчёте, ни в сверке. Без базы балансера секция пропускается с причиной. На 2026-11-03: 38 задач, расходятся три на gpt-5.6-sol (omp считал $4/$20 за миллион, agent-lb $5/$30, 78% счёта) и одна claude (76%); gpt-6.1-sol, gpt-6.1-terra и gpt-5.6-luna совпадают точно.
- `post_review`: ревью правок исполнителей с `review_by` (`result.meta.review`). Считает ревью по вердиктам (`pass`, `fail`, `unknown` — отчёт без вердикта, `skipped` — ревью не состоялось), причины `skipped` по ключу до первого двоеточия (`max_hops`, `perimeter`, `unavailable`, `budget`, `review failed`, `timeout`), эскалации `review_failed` и исход их цепочек по последнему звену (`completed`, `not_completed`, `in_flight`), и цену самих ревью (`usage.cost_usd` задач-потомков из `meta.review.task_id`). Ревью, которые вызывающий заказал сам, в секцию не входят. Рекомендация появляется, когда `skipped` больше 20% ревью: работа уходит в рабочую копию без ревью.
- `feedback`: явные оценки из `POST /tasks/{id}/feedback`. Для каждой задачи берётся последняя оценка, поэтому покрытие показывает, насколько git-эвристика acceptance проверена человеком. В конце отчёта `recommended actions` связывает измеренные потери с конкретным следующим шагом; рекомендации не меняют конфиг автоматически. Если у experiment arm меньше 30 наблюдений, replay прямо предупреждает не менять routing.
- `router_vs_static`: для каждого решения Jev без guard'а `capability.select` на текущем конфиге запускается дважды, с ответом Jev и со статическим правилом (`--baseline-tier`, по умолчанию `balanced`, без вопроса о суждении). Ответ о периметре у обоих общий, порог берётся из `routing.corporate_min_confidence`. Высокое совпадение означает, что Jev можно заменить правилом. Доля `completed` при совпадении и при расхождении смешана со сложностью задач: Jev уводит в `strong` как раз трудные задачи.
- `exploration`: несмещённое сравнение задач с явной меткой `exploration_arm`. Для `explore` и `jev` выводятся число задач, доля `completed`, доля закоммиченных дифов и доля сохранённых строк из той же логики `acceptance`. Незавершённые задачи в доли не входят, их число стоит в `in_flight`. Crossover (назначен `explore`, но статический исполнитель был недоступен и запустился выбор Jev, `exploration_crossover`) остаётся в `explore` по назначению и считается в `crossover`. Если хотя бы в одной группе меньше 30 задач, replay печатает предупреждение. Старые решения Jev без метки не считаются контрольной группой.

Чтобы собирать данные, задайте `routing.explore_share: 0.1`. Это рекомендуемое значение: 10% пригодных задач получит статический исполнитель тира `balanced`, остальные сохранят выбор Jev. При `0.0` эксперимент выключен. Override, эскалации, follow-up, review и fallback в выборку не попадают; guards и корпоративный периметр действуют до подмены.

JSON-отчёты сохраняются в `evals/reports/` (этот каталог игнорируется Git).

## Правила продовых задач

`prod: true` в MCP `route`, `dispatch`, `dispatch_to` (CLI `--prod`) требует включённого исполнителя с `corporate: true` независимо от `routing.corporate_perimeter`. Jev не спрашивает о корпоративных данных, решение получает `meta.perimeter: prod`. Fallback, эскалации, переадресация, follow-up, вложенные задачи и ревью наследуют требование. Явный внешний исполнитель, даже у корневой задачи, получает `guard: perimeter`; конфиг без включённых корпоративных исполнителей тоже даёт отказ до запуска.

Для автоматического ревью под любым обязательным периметром используется `executors.<имя>.perimeter_review_by`, а не `review_by`. Ревьюер обязан быть `corporate: true`, можно указать самого исполнителя: это отдельный запуск только для чтения с чистым контекстом. Без настройки ревью `skipped` с причиной `perimeter: no corporate reviewer`, внешний ревьюер не вызывается. Такие ревью входят и в `post_review`, и в продовую сводку, если задача под `prod`.

«Prod data rule» в Task Package исполнителя и ревьюера требует выводы и цифры вместо сырых данных. Нельзя писать строки таблиц, целые логи, секреты, строки подключения и персональные данные в сообщения, отчёт или файлы. Допустима одна строка доказательства с маскировкой. Перед записью результата `dispatch/redact.py` дополнительно очищает `summary` и `error`: приватные ключи PEM, пароли в строках подключения, JWT, Bearer и пары ключ-значение с секретами. `meta.redacted` хранит только число замен и имена полей; произвольные данные, файлы, логи и прочие поля результата очисткой не покрыты.

Task Package любой задачи и ревью запрещает обход отказов hook, guard или песочницы через другой инструмент, eval или скрипт. Исполнитель прекращает запрещённое действие и сообщает отказ с причиной.

## Надзор во время работы

```bash
uv run python -m evals.supervision          # бесплатно: строгий формат continue/stop
uv run python -m evals.supervision --live   # платно: локальный omp Sol, без HTTP API и демона
```

`parser_cases.jsonl` фиксирует схему вердикта: для `stop` нужны факты, неизвестные поля, команды, нестрогие типы и Markdown не принимаются. `semantic_cases.jsonl` содержит размеченные отклонения и отрицательные примеры: долгие тесты, тихое рассуждение, нормальное исследование, одиночная ошибка и внедрённые инструкции. Живой прогон использует тот же `judge`, модель и изолированный профиль, что демон. Порог accuracy — 0.9 (`--threshold`); дополнительно нужны ноль ложных остановок нормальной работы и ноль ошибок запуска/формата. Каждая строка JSON показывает решение, причину, длительность, токены и цену, если CLI их сообщил. Недоступная модель даёт провал, без подмены.

Это проверка семантики на ограниченном корпусе, не гарантия для всех задач. Жизненный цикл проверяет `tests/test_supervision.py`: настоящий локальный fake-процесс, группа дочерних процессов, остановка после `continue`, гонки завершения/отмены, ожидание слота и сохранение остановленного worktree без интеграции.

## Детерминированные offline-сьюты

Три бесплатных прогона без сети, живых CLI и демона. Код возврата 0, если все случаи сошлись.

### `evals.executors` — argv и парсинг omp-адаптера

```bash
uv run python -m evals.executors
```

Корпус `evals/executors/corpus.jsonl` реплеит два вида контрактов адаптера без запуска CLI: сборку argv (task-запуск идёт в режиме `--approval-mode yolo`, ревью форсирует `--tools read,grep,glob`; корпоративная модель добавляет `--profile x5` и явную `--model`) и разбор событий CLI (ошибка ключа, отсутствие сети, отсутствие блока результата → `partial`, лимит `--max-cost`, usage). Корпус резолвится рядом с модулем, не по cwd вызывающего.

### `evals.scheduling` — ёмкость задач и ревью

```bash
uv run python -m evals.scheduling            # все сценарии
uv run python -m evals.scheduling --seed 42  # другой расклад стресс-гонки
```

Dispatcher поднимается in-process на гейт-адаптерах: ревью стартует при насыщенных задачных слотах, лишние ревью ждут в своей ёмкости, отмена освобождает ровно свой слот, вложенная работа (hop > 0) идёт мимо пулов, после дренирования нет утечек семафоров, cwd-локов и событий. Подробности — [`evals/scheduling/README.md`](scheduling/README.md).

### `evals.workflow` — контракты в отрендеренном TaskPackage

```bash
uv run python -m evals.workflow
```

Сьют строит настоящие `TaskPackage` через `build_task_package` и передаёт их в `render_prompt`: task и review, все адаптеры, три режима контекста, вложенный hop. Сравниваются секции готового промпта с контрактами: ответственность за проверки, запрет commit/push, ревью только для чтения. Это не скоринг «canned reports» и не доказательство того, что LLM подчиняется инструкциям: eval не запускает модель и не разбирает её отчёты — он проверяет только, что AgentDispatch отрендерил нужные инструкции в итоговый промпт. Поведение живого агента проверяет платный `evals.smoke`.

## Replay

| Дата | Задач | Сбои исполнителя | Запуски к лежавшему исполнителю | Недоделка перед эскалацией / конфликт следующего | `partial` из-за формата отчёта |
|---|---:|---:|---:|---:|---:|
| 2026-09-30 | 120 | 12 (quota 4, network 6, capacity 1, auth 1) | 7, 180 мин | 4 / 3 | 2 из 12 |

Прогон на телеметрии 22-30 сентября до остывания, удержания интеграции и мягкого разбора уверенности. Шесть из семи лишних запусков это `omp/sol` без сети вечером 23 сентября: каждый висел 30 минут до жёсткого таймаута, и каждую задачу потом переделывал `claude/opus`.

| Дата | Исходных задач | Впустую | Закоммичено / неизвестно | Строк исполнителя в коммите | Jev = статика `balanced` |
|---|---:|---:|---:|---:|---:|
| 2026-10-09 | 370 | 80 (22%, 296 мин): guard 25, cancelled 20, task_failed 16, quota 15 | 41 из 41 / 145 | 82% по 39 дифам (kept 27, reworked 10, rewritten 2) | 101 из 153 (66%) |

Прогон 22.09-09.10. Половина пустых делегирований приходится на собственные отказы демона (`sibling count`) и отмены, а не на исполнителей. Из 145 `unknown` 130 дифов лежали в удалённых каталогах (scratch-репы smoke-прогонов, снесённые worktree), ещё 15 каталогов уже не git. Факт коммита ничего не различает: этот процесс коммитит всё.
