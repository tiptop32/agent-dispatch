# AgentDispatch

Сервис маршрутизации coding-задач между Claude Code и omp. Архитектура в `docs/architecture.md`, план и история решений в `docs/plans/`.

## Команды

- `uv sync`; `uv run pytest tests -q` (gate, без сети и без настоящих CLI, ~1 мин из-за вложенного pytest в тестах evals-харнесса)
- `uv run ruff check . && uv run ruff format --check .`
- `uv run pre-commit install` (ruff, detect-secrets, pytest gate)
- `uv run agent-dispatch doctor [--online]`, `uv run agent-dispatch serve`
- Evals (платные): `uv run python -m evals.routing`, `uv run python -m evals.smoke --executors omp`
- Replay по живой телеметрии (бесплатно): `uv run python -m evals.replay [--json]`

## Правила проекта

- Jev не делает side effects: он только выбирает исполнителя. Guards, таймауты, запуск живут в коде.
- Ключи из `Settings.secrets` никогда не попадают в env дочерних процессов: их вырезает `executors/env.py:child_env`. Любая строка `Missing environment variable: <...>_API_KEY` в начале `error` — это отказ авторизации, который `health.classify_failure` распознаёт по паттерну; та же фраза после префикса (`MCP server x failed: ...`) это сбой MCP-сервера и не считается. Подсказка `doctor` смотрит только на ключи env-файла (`Settings.secrets`). Отдельной проверки ключа в `doctor` нет: `executor:<имя>` запускает CLI и краснеет сам, а если CLI назвал секрет, лежащий в env-файле agent-dispatch, `doctor` добавляет подсказку (без значения).
- Env дочерних CLI также без `CLAUDECODE`/`CLAUDE_CODE_*`, иначе `claude -p` отказывается работать вложенно.
- MCP и демон используют установленный `agent-dispatch` как non-editable копию uv tool. После изменений кода переустановите её перед добавлением новых ключей в пользовательский конфиг: проверка `install` в `doctor` находит устаревшую копию.
- Автостарт демона (`mcp/autostart.py`) задаёт `cwd=data_dir`: `python -m` ставит cwd первым в `sys.path`, поэтому запуск из рабочей копии подхватывал её код вместо установленного, а свежие шаблоны давали `UndefinedError: 'prod' is undefined` (2026-11-04).
- Ответы MCP по умолчанию компактные, потому что вызывающая модель повторно читает каждый байт на каждом ходе; полный JSON возвращается только с `verbose`.
- Инкремент hop только в демоне (`AGENT_DISPATCH_HOP = hop + 1`); прокси передаёт значение без изменений.
- Исполнители и модели задаются только в config.yaml (`executors`, `escalation`); в коде нет списка моделей.
- Jev выбирает уровень работы (`capability`: fast/balanced/strong), а не имя модели: имена неразличимы для модели и дают плоское распределение. Соответствие уровня и исполнителя живёт в `routing/capability.py` и поле `tier` конфига.
- `max_capability` ограничивает выбор роутера сверху (`fast < balanced < strong`), но не явный `executor` и не цепочку эскалации; исходный уровень остаётся в `decision.meta.capability_uncapped`. Совет Jev «нужно суждение» потолок не обходит: reasoning-исполнитель берётся только не выше потолка, иначе потолок остаётся с заметкой. Корпоративный периметр сильнее потолка.
- `corporate: true` у исполнителя это периметр данных, а не цена: он выигрывает у `judgment` при выборе.
- `prod: true` в MCP `route`/`dispatch`/`dispatch_to` (`--prod` в CLI) всегда требует `corporate: true`, даже при `routing.corporate_perimeter: false`: `decision.meta.perimeter = "prod"`. Роутеры (Jev и `claude_local`) не вызываются вовсе, текст задачи им не уходит: `decide_with_fallback` выбирает статически (`_prod_decision`, тир `STATIC_BASELINE_TIER` с потолком `max_capability`) среди `corporate: true`, `router: fallback`, заметка `prod: routers skipped`. Так же у наследников линии и у вложенного MCP `route` (`route_only` наследует периметр родителя, как `_prepare`). Требование наследуется по всей линии (`escalated_from`, `followup_of`, `parent_task_id`), включая переадресацию, и сильнее `answered`/`unknown`; явный внешний `executor` даже корневой задачи получает `guard: perimeter`. Без включённого корпоративного исполнителя запрос отклоняется до запуска.
- `TaskPackage.prod` добавляет «Prod data rule» (`templates/prod_data_rule.md.j2`) задаче, ревьюеру и возобновлённому follow-up: только выводы и цифры, без строк таблиц, целых логов, секретов, строк подключения и персональных данных в сообщениях, отчёте и файлах; допустима одна строка доказательства с маскировкой. `dispatch/redact.py` в `_finalize` дополнительно маскирует в `summary` и `error` приватные ключи PEM, пароли строк подключения (и с пустым логином, и с `/` в пароле), JWT, Bearer (заглавный с любым токеном, кроме короткого строчного слова; другое написание только с цифрой или символом в токене, чтобы «bearer authentication» не трогалась) и пары ключ-значение с секретами (`pwd` только после разделителя: `PWD=`/`OLDPWD=` это каталоги); `meta.redacted = {replacements, fields}` хранит число замен и имена полей, без значений. Это страховка, не полная очистка данных и не замена правилу.
- Отказ инструмента нельзя обходить: Task Package любой задачи и ревью запрещает повторять запрещённое hook, guard или песочницей действие через другой инструмент, eval или скрипт; исполнитель прекращает это действие и сообщает отказ с причиной.
- Ответ Jev о корпоративных данных это `noul`, и его уверенность (`|p - 0.5| * 2`) бывает около нуля. Порог `routing.corporate_min_confidence` (по умолчанию 0, то есть прежнее поведение) не даёт сужать пул по монетке. Поднятие порога ослабляет периметр данных — это решение человека, а не дефолт.
- Для обычных задач без `prod` вопрос о корп. данных требуется всегда, кроме случая «периметр выключен или в конфиге нет включённого `corporate: true`» (`capability.perimeter_applies`). Считается по конфигу, а не по доступным кандидатам: остывание всех корпоративных исполнителей не открывает периметр. Отсутствие ответа (fallback роутеров, `claude_local`, который вопрос не задаёт, короткий путь «один кандидат») означает «неизвестно»: пул сужается до периметра (fail closed), исход в `decision.meta.perimeter` (`answered` по ответу Jev, `unknown` без него). При применимом автоматическом периметре короткого пути «один кандидат» нет: вопрос задаётся всегда, иначе ответ пришлось бы угадывать для всей линии задачи. Бэкенд `claude_local` вопроса не задаёт, поэтому с ним (и при каждом отказе Jev) обычные задачи при конфиге с `corporate: true` всегда идут внутрь периметра: этот fail closed можно ослабить только `corporate_perimeter: false`. Одно правило живёт в `capability.perimeter_required`.
- Fallback и эскалация периметра не покидают: слабое решение (`low_confidence`, `low_margin`) и путь «все роутеры упали» выбирают замену только среди `corporate: true`; если в `fallback_chain` исполнителя периметра нет, задача остаётся у представителя периметра с предупреждением. Звенья эскалации, переадресация роутеру после сбоя исполнителя и follow-up наследуют требование предка (`Dispatcher._lineage_perimeter`: `prod` запроса и `decision.meta.perimeter` по `escalated_from`, `followup_of` и `parent_task_id` из базы, переживает рестарт демона): внешние звенья цепочки пропускаются, а роутер на переадресации и follow-up выбирает только из `corporate: true`, даже если Jev теперь ответил «не корпоративное». Когда корпоративных звеньев не осталось и переадресации нет, цепочка останавливается с `result.meta.escalation_stopped: perimeter`. Последний рубеж, `Dispatcher._perimeter_refusal`, отказывает внешнему исполнителю задачи под периметром до запуска (`guard: perimeter`, в том числе когда все корпоративные остывают или вложенный dispatch задаёт внешний `executor`). Только у корневой задачи без `prod` и без предка под периметром явный `executor` остаётся решением владельца данных: отказа нет и требования периметра он не ставит, даже корпоративный, поэтому его эскалация и вложенные задачи могут уйти наружу. Запуски вне требуемого периметра считает `evals.replay` (`perimeter_violations`, порог 0).
- Неполный ответ Jev это ошибка роутера: `noul` без конечной вероятности из [0, 1] (`invalid noul answer`), ответ `corporate_data` не типа `noul` и незаданный вопрос `corporate_data` (`missing answer: corporate_data`) дают `RouterError`; `confidence` ответа `capability` тоже обязан быть конечным из [0, 1] (NaN обходил `low_confidence`) и обычный fallback роутеров, периметр при этом всё равно применяется.
- Fallback уважает `max_capability` (`guards.fallback_choice`, общий для слабого решения и пути «все роутеры упали»): исполнитель цепочки берётся не выше потолка; если таких нет или цепочка недоступна, остаётся (уже ограниченный) выбор роутера, а не `top1` из оценок выше потолка. Периметр сильнее потолка и здесь.
- `routing.corporate_perimeter: false` выключает автоматический периметр для обычных задач: вопрос `corporate_data` Jev не задаётся, пул не сужается. Требование `prod` у задачи или предка остаётся обязательным. По умолчанию `true`; выключение это решение владельца данных в его конфиге.
- Если внутри периметра нет исполнителя нужного тира, `select` пишет это в `selection_notes`, а не понижает уровень молча.
- `partial` с `parse_error` и пустым `changed_files` эскалируется (`no_result`): исполнитель не отчитался и ничего не тронул. При непустом `changed_files` эскалации нет — работа есть, судит о ней вызывающий по дифу, повторный запуск лёг бы поверх. `changed_files` сравнивает отпечатки содержимого файлов (`executors/workspace.py`; пути porcelain хешируются от корня репозитория, а не от `cwd`, снимки снимаются в `asyncio.to_thread`), поэтому переписанный файл, который был грязным ещё до запуска, тоже считается работой, как и откат исполнителем чужой правки.
- `partial` с `no result block`, непустым `changed_files`, без `error` и с `meta.session_id` получает один дозапрос отчёта в той же сессии (`dispatch/report_recovery.py`, шаблон `report_only.md.j2`, предел `execution.report_recovery_timeout_seconds`, 0 выключает) до `verify`. Удачный отчёт заменяет статус, итог и тесты, файлы объединяются, метаданные запуска остаются от первого; неудачный оставляет `partial` с `meta.report_recovery: failed: ...`. Счётчик в `evals.replay` (`report_recovery`). Ревью дозапрос не получает.
- Таймаут или `stalled` с непустым `changed_files` передаёт начатую работу только при наличии допустимого следующего звена (периметр, `allow_escalation`, бюджет). Worktree-наследник получает патч только непосредственного предка; in_place работа уже на месте. `meta.handoff` хранит `from_task`, `mode: patch|in_place`, `apply_failed`; при ошибке применения звено стартует с HEAD. Без звена сохраняется прежний результат: таймаут с правками — `partial`, без правок — `failed`.
- Таймаут запуска: `timeout_seconds` запроса, затем `executors.<имя>.timeout_seconds`, затем `routing.default_timeout_seconds` (`Settings.timeout_for`); тот же срок пишется в Task Package. `meta.last_output_age_s` фиксируется до SIGTERM, у нестриминговых адаптеров — `null`. Replay (`timeouts`) различает `active` (вывод за последние 120 с) и `quiet`.
- Сторож omp разбирает события потока, а не только stdout/stderr. Проверка каждые `execution.watchdog_interval_seconds: 300`: без открытого инструмента предел `idle_timeout_seconds: 300`, с открытым — `watchdog_tool_idle_seconds: 900`; `watchdog_repeat_limit: 6` одинаковых подряд хешей «инструмент + аргументы + результат» даёт `stalled: looping`, молчание — `stalled: idle`. Медленный прогресс не прерывается. `meta.watchdog` хранит причину, `idle_s` или `repeats`, `tool_open`; остывания нет. Ноль `idle_timeout_seconds` отключает предел молчания без открытого инструмента, но не остальные проверки; жёсткий таймаут остаётся. У нестримингового Claude сторож выключен.
- Остывание исполнителя (`routing.failure_cooldown_seconds`) включается только по узнаваемым сообщениям CLI в `error` и по строке адаптера omp `omp: no model response` (модель не ответила ни разу) (`executors/health.py`). Слова из вывода агента и ошибки MCP-серверов в stderr не считаются: задача про rate limiting не должна выключать исполнителя. Голый таймаут тоже не считается, агент мог работать.
- Обрыв транспорта (`connection reset/closed`, `websocket ... error`, `sequence_number regressed`, `transport error`) считается сбоем исполнителя (`network`, внутренний класс `transport_error`) только с начала строки `error`, после необязательного `error:` и одного слова провайдера (`health._TRANSPORT_LINE`), и только для `failed` или `partial` с `meta.cli_error`: `MCP server x failed: connection closed` и слова агента не выводят группу из ротации.
- Повтор транспорта (`execution.transport_retry_*`) делает только адаптер с `reports_transport_before_output` (omp): отпечаток рабочей копии снимается до запуска лишь при `transport_retry_attempts > 0`, повтор идёт при обрыве до первого ответа модели, неизменённой копии и в пределах `transport_retry_max_seconds`. Эскалация подавляется (`meta.escalation_suppressed: transport_error`) только когда повтор действительно был (`meta.retry_count`); без повтора обрыв эскалируется, как раньше. `evals.replay` (`outcomes`) считает `retry_recovered` (повтор довёл до completed) и `escalation_suppressed`: рост второго при нуле первого значит, что подавление теряет результаты.
- Preflight внешнего роутера живёт только в `JevRouter.decide` (`routing/preflight.py`): его проходят и dispatch, и `doctor --online`, проба которого берёт первый существующий `router.external.trusted_roots`. Backend `jev` без доверенного корня и без `allow_unknown_projects` даёт FAIL `router-external` в `doctor`: иначе каждый вызов Jev молча уходил бы в `claude_local` и внутрь периметра. `explore_share > 0` при backend не `jev` даёт WARN: эксперимент сравнивает решения Jev.
- `retryable` в отказе guard истинен для `unavailable`, `max_children` и `budget` (снимаются со временем); `FollowupError.code` (`task_in_progress`, `no_executor_run`, `worktree_not_integrated`) отдаётся API как `detail.code`, текст сообщения не разбирается. Компактный ответ MCP не печатает пустые поля `meta` и `error_code`, равный `failure_class`.
- Исчерпанный лимит держит исполнителя до сброса из сообщения CLI (`health.py:parse_reset`) и выводит всю `limit_group` (claude/*, omp/*). Лимит расходов и `limit_reset: recheck` перепроверяются через `routing.quota_cooldown_seconds`: их снимают раньше названного срока (человек поднял лимит, балансер отдал свободный аккаунт). Остывание лежит в таблице `cooldowns` и переживает перезапуск демона. Ложные блокировки проверяет `evals.replay`: в `avoidable_runs` не должно быть `completed`.
- `ConcurrencyLimitModel` и `Parallel processed requests limit exceed` — `model_busy`, не квота аккаунта: остывает только этот исполнитель на `routing.busy_cooldown_seconds` (120 с), соседей `limit_group` это не затрагивает. Прочие 429 сохраняют правила квоты.
- `routing.review_only` (по умолчанию `omp: [claude]`): задачу на правку от этого источника нельзя отдать этим адаптерам ни через роутер, ни через цепочку эскалации, разрешено только `kind: review`; источники `codex` и `opencode` остаются валидными для старых строк БД и follow-up по старым задачам. Ревью идёт в режиме только чтения и всегда in_place: worktree от HEAD не видит незакоммиченного диффа.
- `routing.explore_share` (по умолчанию `0.0`) детерминированно делит пригодные решения Jev по `task_id`. В arm `explore` запускается статический исполнитель тира `balanced`, но выбор Jev сохраняется в `routing_decisions.judgments_json`; рекомендуемое для измерения значение `0.1`. Эксперимент не касается override, эскалаций, follow-up, review и fallback и не обходит guards. Если статический исполнитель недоступен, запускается выбор Jev, но arm остаётся `explore` (`exploration_crossover`): перенос в контрольную группу смещал бы сравнение.
- Второй демон для сквозной проверки (свой порт, `AGENT_DISPATCH_CONFIG_DIR`/`AGENT_DISPATCH_DATA_DIR`) останавливать по pid из его `serve.json`, а не `pkill -f "agent_dispatch.cli serve"`: автостарт MCP запускает рабочий демон той же командой, и 2026-10-03 так был убит рабочий демон на 7433.
- Обычно эскалируемая работа не интегрируется (`integration_held`), следующее звено стартует с HEAD. Исключение — передача начатой работы после timeout/stalled: наследник получает патч непосредственного предка. Без эскалации упавшая работа интегрируется как раньше.
- В режиме `execution.workspace_mode: worktree` исполнитель работает в отдельном git worktree от HEAD, а результат возвращается патчем; lock на `cwd` берётся только на время интеграции.
- Lock `_cwd_lock` ключуется корнем конкретной рабочей копии (`git rev-parse --show-toplevel`, `dispatcher._cwd_lock_key`), а не строкой `cwd` и не общим git dir: задачи с `cwd` в корне и в подкаталоге делят один git-индекс и должны идти по очереди, а отдельные `git worktree` одного репозитория — независимые копии, им параллельность нужна. Вне git ключ — разрешённый `cwd`.
- Исполнитель не коммитит (запрещено в Task Package), коммитит демон: `worktree.commit` на ветке задачи, с `--no-verify`. Хуки репозитория на служебном коммите не гоняются осознанно — pre-commit с полным прогоном тестов падал бы на недоделанной задаче. Гейт — коммит вызывающего после ревью дифа.
- `worktree.build_patch` считает диф от `Worktree.base`, а не от HEAD: после промежуточного коммита `diff --cached HEAD` вернул бы пустоту (есть тест на равенство патча до и после коммита).
- `integrate: branch` оставляет ветку без worktree. Такие ветки показывает `worktree.list_branches`, иначе они копились бы незаметно.
- «Демон запущен» решает порт, а не pid: `serve_state.is_running` это живой pid И занятый порт. `os.kill(pid, 0)` истинен и для зомби, и для процесса, застрявшего в shutdown, а такой pid в `serve.json` запирал старт нового демона навсегда.
- Отмена задачи, перезапуск демона и сбой интеграции worktree не удаляют: в нём лежит работа исполнителя, и выбрасывать её демон не вправе. Но путь и ветка обязаны попасть в `result.meta` (`_note_kept_worktree` на срыве, `_worktree_meta` в `recover_stale`), иначе дерево не видно ни в `status`, ни вызывающему. Единственный сборщик мусора — `agent-dispatch worktrees --clean`, его запускает человек. `worktrees --all` читает все деревья из каталога данных, связывает их с репозиториями через `.git` и показывает статус задачи из БД. `--all --clean` удаляет только деревья готовых задач без активного `cwd`; каталог с исчезнувшим репозиторием удаляется напрямую. `doctor` предупреждает о деревьях старше семи дней.
- `worktree.apply_patch` атомарен: перед `git apply --3way` снимаются копии затронутых файлов и индекса, при любой ошибке они возвращаются. Голый `--3way` при конфликте оставлял маркеры и частично применённый, проиндексированный патч в рабочей копии вызывающего при `integrated: false`; `--3way --check` на git 2.51 для проверки не годится.
- Вложенный `dispatch` с `cwd` внутри чужого worktree получает родителя и `hop = parent.hop + 1` в `submit` (`_inherit_worktree_parent`), даже если MCP-клиент не передал `AGENT_DISPATCH_*`. Клиент передаёт их через `env_vars` в `[mcp_servers.agent-dispatch]`, это проверяет `doctor` (`client-env-vars`). Без этого ребёнок вставал в корневую очередь за своим родителем и терял `cwd`, когда родитель удалял дерево.
- `_drop_worktree` не удаляет дерево, пока в нём `cwd` незавершённой задачи (`meta.worktree_kept: active children`).
- `max_children` считает только детей с назначенным исполнителем, без самой задачи и внутренних потомков автоматического ревью. Отказанные попытки квоту не занимают; отказ советует ждать работающих детей через `status(task_id, wait_seconds)`.
- Корневая правка занимает слот группы, затем общий `server.max_concurrent_tasks`; `limit_groups.<группа>.max_concurrent` заменяет `server.max_concurrent_per_group`. `executors.<имя>.max_concurrent` ограничивает только время CLI всех запусков, включая ревью и вложенные задачи, и учитывается в `queue_fallback`. Слот освобождается до ожидания ревью и между раундами; вложенный запуск того же исполнителя делит слот предка, не захватывая второй. Ревью сохраняет отдельный пул, вложенные задачи не берут корневые слоты. Событие `slot` отражает ожидание.
- После ожидания слота `_execute` перепроверяет доступность исполнителя: задача, дождавшаяся слота после остывания исполнителя, получает `failed` («became unavailable») и эскалацию вместо запуска.
- В worktree-режиме `render_prompt` переписывает абсолютные пути корня репозитория вызывающего на путь worktree (граница пути строгая, `/repo-old` не трогается). Ревью omp получают разрешение на чтение `/tmp`, задачи нет.
- `verify` в запросе это shell-команды, которые демон запускает сам после исполнителя (`dispatch/verify.py`), до первой упавшей, с `execution.verify_timeout_seconds` на команду и env `child_env` без секретов. Упавшая проверка сильнее самоотчёта `tests`: `completed` становится `partial`, причина эскалации `verification_failed`. И наоборот: при прошедшей проверке самоотчёт `tests: failed` эскалацию не вызывает (`escalation.should_escalate`), отчёт остаётся в результате для вызывающего. Вывод команды не кладётся в `error`, иначе `health.classify_failure` принял бы текст теста про rate limit за лимит CLI. Ревью и незавершённые результаты (`failed`, `needs_*`) не проверяются.
- `executors.<имя>.review_by` и `perimeter_review_by` принимают строку или упорядоченный список. Вне периметра используется `review_by` (нельзя себя), внутри — только `perimeter_review_by` (можно себя, требуется `corporate: true`); неизвестные имена отвергает конфиг. Без корпоративного ревьюера — `skipped`, внешний не вызывается. Авто-ревью идёт после verify для `completed` с правками, до интеграции; потомки read-only, in_place, без эскалации и вне `max_children`. `pass`, `skipped` и `unknown` продвигают к следующей ступени; `fail` останавливает и даёт `partial` с причиной `review_failed`. Итоги в `meta.review` и `meta.review_stages`, замечания ограничены 1500 символами и передаются в context, не в error. Ревью видит задачу и диф; worktree очищается от артефактов ревью, отмена родителя отменяет ревьюера.
- В worktree текст задачи ревьюера проходит `rewrite_repo_prefix`, неразрешимый `review_base` даёт ошибку пакета, а сбой очистки артефактов отмечается `meta.review_artifacts_kept`. In_place ревью ограничивается `changed_files`, поскольку `git diff HEAD` содержит и правки вызывающего. Замечания накапливаются в context звеньев; `evals.replay` считает `post_review` без повторного подсчёта цепочки. Ревью ждёт не дольше таймаута ревьюера плюс 60 с.
- `execution.review_fix_rounds: 1` даёт общий на звено бюджет раундов после `verification_failed` или ревью `fail`. Это не follow-up: тот же исполнитель продолжает сессию в том же cwd внутри запуска; затем снова verify и только проваленная ступень ревью, пройденные ступени не повторяются. Перед раундом проверяется бюджет; `0` отключает. `changed_files` объединяются, usage/cost складываются, `meta.fix_rounds` хранит расход самого раунда; skipped/unknown раунда не запускают. После исчерпания — обычная эскалация.
- В worktree проверка идёт после коммита работы на ветку задачи и в подкаталоге дерева, соответствующем `cwd`; затем дерево откатывается к коммиту (`worktree.discard_changes`), чтобы артефакты проверки не попали в патч. Поэтому `worktree.commit` при чистом индексе возвращает HEAD, если он ушёл от `base`, а не `None`. In-place артефакты остаются в рабочей копии, как после ручного прогона.
- Цену задачи (`usage.cost_usd`) CLI считает по своему каталогу, agent-lb по своему `pricing.py`, и они расходятся молча (gpt-5.6-sol: omp видел 78% счёта). `evals.replay` (`cost_drift`) сверяет их по `meta.session_id` с `request_logs` балансера, допуск 10%.
- Потолки расходов выключены по умолчанию (`null`): `routing.max_chain_cost_usd` останавливает эскалацию, когда цепочка с подзадачами звеньев дошла до него (`meta.budget`); `routing.daily_cost_limit_usd` отказывает (`guard: budget`) новым задачам и подзадачам до роутера, пока расходы локальных суток не ниже лимита. Оба потолка проверяются и при планировании эскалации (`_budget_stop`): звено, которое бюджет не пустит, не создаётся, и работа не удерживается ради него (`integration_held`). Считается только цена, которую сообщает CLI.
- Follow-up (`POST /tasks/{id}/followup`, MCP `followup`, CLI `followup`) продолжает последнее звено цепочки эскалации тем же исполнителем, всегда in_place: worktree от HEAD не видит перенесённого незакоммиченного результата. Работа не в рабочей копии (`integrated: false` с патчем, веткой или оставшимся деревом) — отказ 409, а не запуск поверх пустоты. Звено, которому guard отказал до исполнителя, пропускается. Остывающий исполнитель — follow-up идёт роутеру. MCP передаёт источник, hop и родителя вызывающего: guards (`review_only`, глубина) судят его, а не автора исходной задачи. Решения follow-up — чистые функции в `dispatch/followup.py`.
- Сессию CLI продолжает только тот же исполнитель в том же каталоге, а у omp ещё и с тем же `--session-dir` и профилем (claude ищет сессии по cwd; дерева прошлого запуска уже нет): тогда промпт короткий (`followup_resumed.md.j2`), иначе в Task Package идёт итог прошлой попытки. id сессии лежит в `result.meta.session_id`: claude получает его от демона (`--session-id`), чтобы продолжить и задачу, убитую таймаутом; omp отдаёт id в первой строке `{"type":"session"}`, адаптер передаёт его в `--resume`. Продолжение, упавшее до работы (не лимит, не таймаут, без изменений), повторяется один раз с нуля (`meta.resume_failed`).
- `submit` пишет событие `git` (`common_dir` абсолютный, `branch`, `null` при detached) для `cwd` в git до своего ответа, а не фоном: вызывающий вправе удалить worktree сразу после `submit`. `evals.replay` (`acceptance`) по нему судит дифы, когда вызывающий удалил свой worktree после слияния: `git --git-dir` с `log --exclude=refs/stash --all`, служебные коммиты демона не в счёт. У старых задач без события — живой предок в git или соседние checkouts с одним общим git dir; соседи из разных реп дают `unknown: ambiguous`, а не догадку; репа из догадки, в истории которой нет ни одного файла задачи, даёт `unknown: unverified_repo`. Живой `cwd` в git судится как раньше, по своему HEAD; каталог без git (остаток worktree с `.idea`) — как удалённый.
- MCP пишет `<data_dir>/mcp_responses.jsonl`: `ts`, `tool`, `task_id` (у route `null`), `bytes` текста ответа в UTF-8, `verbose`. Текст ответа и задачи не сохраняется; ошибка записи не ломает ответ. Replay связывает байты с корнем (`caller_bytes`), считает `watchdog`, `handoff`, `fix_round`, `review_stages`; отсутствие метрик не означает ноль. Недельные критерии плана проверяются после релиза; измеренные улучшения пока не заявляются.
- `meta.diff_stat = {files, added, removed}` считает фактическую дельту задачи по `changed_files`, не исходные грязные правки вызывающего; бинарные изменения увеличивают только `files`.
- `config.example.yaml` равен `agent_dispatch/config_default.yaml` (есть тест).
- Корпоративные исполнители (`corporate: true`) используют только модели реестра внутренних моделей AI-Run (`copilot-x5/x5-airun-*`, https://instructions.x5.ru/airun/reestr-vnutrennikh-modeley; статус https://stats.airun.x5.ru/, API за SSO). Шлюз copilot-x5 ещё принимает старые алиасы (`copilot-code-flash`, `x5-airun-small-coder`), но их нет ни в реестре, ни в `/v1/models`, и контур за ними не подтверждён; `subscription/*` на том же шлюзе внешние. Есть тест на дефолтный конфиг.

- omp запускается со stdin=DEVNULL, потому что без TTY omp ждёт EOF и висит.
- Каждый запуск omp получает `--config ~/.omp/agent/dispatch-overlay.yml` с `retry.maxRetries: 1`, потому что повторами занимается эскалация диспетчера.
- omp запускается с `NODE_USE_SYSTEM_CA=1`, потому что корпоративный RootCA copilot-x5 лежит в системном Keychain, а bun без флага доверяет только встроенному набору (opencode собран с `--use-system-ca`). Корпоративные исполнители omp запускаются с `--profile x5`, потому что профиль x5 держит периметр и для сабагентов omp (`task`, `prewalk`, `advisor`).
- Ключ балансера omp берёт сам через `apiKey: "!…"` из `omp-setup/bin/lb-key`, а диспетчер вырезает `AGENT_LB_API_KEY` из env omp, потому что окружение запускающего процесса доходит до bash-агента.
- `codex-env-vars` заменён на проверки `omp-mcp-env`, `omp-version`, `omp-x5-profile`, потому что omp передаёт MCP-переменные через собственный конфиг и требует проверяемый профиль.
- `usage` и `cost_usd` суммируются по всем ассистентским `message_end`, потому что каждый ход omp имеет собственный usage.
- Ход omp с `stopReason: error` при непустом `changed_files` даёт `partial` с `meta.cli_error`, без правок остаётся `failed`; `health.classify_failure` распознаёт такой `partial`, поэтому остывание сохраняется. Нестроковые `summary`, `tests.command`, `tests.result` и элементы `changed_files` нормализуются в строки с отметкой `meta.coerced`, не теряя результат работы.
- Код выхода 3 (`--max-cost`) означает бюджет, а не сбой исполнителя.
- Порядок исполнителей внутри тира задаёт пользовательский файл, а не `config_default.yaml`, потому что `load_settings` сохраняет порядок пользовательского конфига.
- Replay судит исторические `codex/*` и `opencode/*` по настройкам omp-преемника (`evals.replay.harness.successor`, таблица из `migrate.py`), потому что старые источники нужны для истории.
- Старый конфиг с adapter codex/opencode не загружается и называет команду `agent-dispatch migrate-config`, потому что новый конфиг использует только omp.
