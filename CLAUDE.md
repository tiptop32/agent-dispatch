# AgentDispatch

Сервис маршрутизации coding-задач между Claude Code, Codex и OpenCode. Архитектура в `docs/architecture.md`, план и история решений в `docs/plans/`.

## Команды

- `uv sync`; `uv run pytest tests -q` (gate, без сети и без настоящих CLI, ~1 мин из-за вложенного pytest в тестах evals-харнесса)
- `uv run ruff check . && uv run ruff format --check .`
- `uv run pre-commit install` (ruff, detect-secrets, pytest gate)
- `uv run agent-dispatch doctor [--online]`, `uv run agent-dispatch serve`
- Evals (платные): `uv run python -m evals.routing`, `uv run python -m evals.smoke --executors codex`
- Replay по живой телеметрии (бесплатно): `uv run python -m evals.replay [--json]`

## Правила проекта

- Jev не делает side effects: он только выбирает исполнителя. Guards, таймауты, запуск живут в коде.
- Ключи никогда не попадают в `os.environ` и в env дочерних процессов: `Settings.secrets` (SecretStr) и `executors/env.py:child_env`.
- Env дочерних CLI также без `CLAUDECODE`/`CLAUDE_CODE_*`, иначе `claude -p` отказывается работать вложенно.
- MCP и демон используют установленный `agent-dispatch` как non-editable копию uv tool. После изменений кода переустановите её перед добавлением новых ключей в пользовательский конфиг: проверка `install` в `doctor` находит устаревшую копию.
- Ответы MCP по умолчанию компактные, потому что вызывающая модель повторно читает каждый байт на каждом ходе; полный JSON возвращается только с `verbose`.
- Инкремент hop только в демоне (`AGENT_DISPATCH_HOP = hop + 1`); прокси передаёт значение без изменений.
- Исполнители и модели задаются только в config.yaml (`executors`, `escalation`); в коде нет списка моделей.
- Jev выбирает уровень работы (`capability`: fast/balanced/strong), а не имя модели: имена неразличимы для модели и дают плоское распределение. Соответствие уровня и исполнителя живёт в `routing/capability.py` и поле `tier` конфига.
- `corporate: true` у исполнителя это периметр данных, а не цена: он выигрывает у `judgment` при выборе.
- Ответ Jev о корпоративных данных это `noul`, и его уверенность (`|p - 0.5| * 2`) бывает около нуля. Порог `routing.corporate_min_confidence` (по умолчанию 0, то есть прежнее поведение) не даёт сужать пул по монетке. Поднятие порога ослабляет периметр данных — это решение человека, а не дефолт.
- `routing.corporate_perimeter: false` выключает периметр целиком: вопрос `corporate_data` Jev не задаётся, пул не сужается. По умолчанию `true`; выключение это решение владельца данных в его конфиге.
- Если внутри периметра нет исполнителя нужного тира, `select` пишет это в `selection_notes`, а не понижает уровень молча.
- `partial` с `parse_error` и пустым `changed_files` эскалируется (`no_result`): исполнитель не отчитался и ничего не тронул. При непустом `changed_files` эскалации нет — работа есть, судит о ней вызывающий по дифу, повторный запуск лёг бы поверх.
- Таймаут с непустым `changed_files` — это `partial` (`error: timeout`, `meta.timed_out`), эскалации нет, судит вызывающий по дифу. Таймаут без изменений остаётся `failed` и эскалируется.
- Зависший исполнитель убивает сторож молчания (`execution.idle_timeout_seconds`, по умолчанию 900): результат `failed` с `stalled: ...` и эскалацией. Жёсткий таймаут остаётся верхней границей. Сторож работает только у адаптеров с `streams_output = True`; `claude -p --output-format json` печатает всё в конце, поэтому у него сторож выключен.
- Остывание исполнителя (`routing.failure_cooldown_seconds`) включается только по узнаваемым сообщениям CLI в `error` и по событиям переподключения codex в хвосте stdout без изменённых файлов (`executors/health.py`). Слова из вывода агента и ошибки MCP-серверов в stderr codex не считаются: задача про rate limiting не должна выключать исполнителя. Голый таймаут тоже не считается, агент мог работать.
- Исчерпанный лимит держит исполнителя до сброса из сообщения CLI (`health.py:parse_reset`) и выводит всю `limit_group` (claude/*, codex/*). Лимит расходов и `limit_reset: recheck` перепроверяются через `routing.quota_cooldown_seconds`: их снимают раньше названного срока (человек поднял лимит, codex-lb отдал свободный аккаунт). Остывание лежит в таблице `cooldowns` и переживает перезапуск демона. Ложные блокировки проверяет `evals.replay`: в `avoidable_runs` не должно быть `completed`.
- `routing.review_only` (по умолчанию `codex: [claude]`): задачу на правку от этого источника нельзя отдать этим адаптерам ни через роутер, ни через цепочку эскалации, разрешено только `kind: review`. Ревью идёт в режиме только чтения и всегда in_place: worktree от HEAD не видит незакоммиченного диффа.
- Второй демон для сквозной проверки (свой порт, `AGENT_DISPATCH_CONFIG_DIR`/`AGENT_DISPATCH_DATA_DIR`) останавливать по pid из его `serve.json`, а не `pkill -f "agent_dispatch.cli serve"`: автостарт MCP запускает рабочий демон той же командой, и 2026-10-03 так был убит рабочий демон на 7433.
- Эскалируемая работа не интегрируется в рабочую копию (`integration_held`), следующее звено стартует с HEAD. Без эскалации упавшая работа интегрируется, как раньше.
- В режиме `execution.workspace_mode: worktree` исполнитель работает в отдельном git worktree от HEAD, а результат возвращается патчем; lock на `cwd` берётся только на время интеграции.
- Исполнитель не коммитит (запрещено в Task Package), коммитит демон: `worktree.commit` на ветке задачи, с `--no-verify`. Хуки репозитория на служебном коммите не гоняются осознанно — pre-commit с полным прогоном тестов падал бы на недоделанной задаче. Гейт — коммит вызывающего после ревью дифа.
- `worktree.build_patch` считает диф от `Worktree.base`, а не от HEAD: после промежуточного коммита `diff --cached HEAD` вернул бы пустоту (есть тест на равенство патча до и после коммита).
- `integrate: branch` оставляет ветку без worktree. Такие ветки показывает `worktree.list_branches`, иначе они копились бы незаметно.
- «Демон запущен» решает порт, а не pid: `serve_state.is_running` это живой pid И занятый порт. `os.kill(pid, 0)` истинен и для зомби, и для процесса, застрявшего в shutdown, а такой pid в `serve.json` запирал старт нового демона навсегда.
- Отмена задачи, перезапуск демона и сбой интеграции worktree не удаляют: в нём лежит работа исполнителя, и выбрасывать её демон не вправе. Но путь и ветка обязаны попасть в `result.meta` (`_note_kept_worktree` на срыве, `_worktree_meta` в `recover_stale`), иначе дерево не видно ни в `status`, ни вызывающему. Единственный сборщик мусора — `agent-dispatch worktrees --clean`, его запускает человек.
- `worktree.apply_patch` атомарен: перед `git apply --3way` снимаются копии затронутых файлов и индекса, при любой ошибке они возвращаются. Голый `--3way` при конфликте оставлял маркеры и частично применённый, проиндексированный патч в рабочей копии вызывающего при `integrated: false`; `--3way --check` на git 2.51 для проверки не годится.
- Вложенный `dispatch` с `cwd` внутри чужого worktree получает родителя и `hop = parent.hop + 1` в `submit` (`_inherit_worktree_parent`), даже если MCP-клиент не передал `AGENT_DISPATCH_*`. Codex передаёт их только через `env_vars` в `[mcp_servers.agent-dispatch]`, это проверяет `doctor` (`codex-env-vars`). Без этого ребёнок вставал в корневую очередь за своим родителем и терял `cwd`, когда родитель удалял дерево.
- `_drop_worktree` не удаляет дерево, пока в нём `cwd` незавершённой задачи (`meta.worktree_kept: active children`).
- `max_children` считает только детей с назначенным исполнителем и без самой задачи: отказанные попытки квоту не занимают.
- После ожидания слота `_execute` перепроверяет доступность исполнителя: задача, дождавшаяся слота после остывания исполнителя, получает `failed` («became unavailable») и эскалацию вместо запуска.
- В worktree-режиме `render_prompt` переписывает абсолютные пути корня репозитория вызывающего на путь worktree (граница пути строгая, `/repo-old` не трогается). Ревью OpenCode получают `OPENCODE_PERMISSION` с чтением `/tmp`, задачи нет.
- `verify` в запросе это shell-команды, которые демон запускает сам после исполнителя (`dispatch/verify.py`), до первой упавшей, с `execution.verify_timeout_seconds` на команду и env `child_env` без секретов. Упавшая проверка сильнее самоотчёта `tests`: `completed` становится `partial`, причина эскалации `verification_failed`. Вывод команды не кладётся в `error`, иначе `health.classify_failure` принял бы текст теста про rate limit за лимит CLI. Ревью и незавершённые результаты (`failed`, `needs_*`) не проверяются.
- В worktree проверка идёт после коммита работы на ветку задачи и в подкаталоге дерева, соответствующем `cwd`; затем дерево откатывается к коммиту (`worktree.discard_changes`), чтобы артефакты проверки не попали в патч. Поэтому `worktree.commit` при чистом индексе возвращает HEAD, если он ушёл от `base`, а не `None`. In-place артефакты остаются в рабочей копии, как после ручного прогона.
- Потолки расходов выключены по умолчанию (`null`): `routing.max_chain_cost_usd` останавливает эскалацию, когда цепочка с подзадачами звеньев дошла до него (`meta.budget`); `routing.daily_cost_limit_usd` отказывает (`guard: budget`) новым задачам и подзадачам до роутера, пока расходы локальных суток не ниже лимита. Оба потолка проверяются и при планировании эскалации (`_budget_stop`): звено, которое бюджет не пустит, не создаётся, и работа не удерживается ради него (`integration_held`). Считается только цена, которую сообщает CLI: codex её не сообщает.
- Follow-up (`POST /tasks/{id}/followup`, MCP `followup`, CLI `followup`) продолжает последнее звено цепочки эскалации тем же исполнителем, всегда in_place: worktree от HEAD не видит перенесённого незакоммиченного результата. Работа не в рабочей копии (`integrated: false` с патчем, веткой или оставшимся деревом) — отказ 409, а не запуск поверх пустоты. Звено, которому guard отказал до исполнителя, пропускается. Остывающий исполнитель — follow-up идёт роутеру. MCP передаёт источник, hop и родителя вызывающего: guards (`review_only`, глубина) судят его, а не автора исходной задачи. Решения follow-up — чистые функции в `dispatch/followup.py`.
- Сессию CLI продолжает только тот же исполнитель в том же каталоге (claude ищет сессии по cwd; дерева прошлого запуска уже нет): тогда промпт короткий (`followup_resumed.md.j2`), иначе в Task Package идёт итог прошлой попытки. id сессии лежит в `result.meta.session_id`: claude получает его от демона (`--session-id`), чтобы продолжить и задачу, убитую таймаутом; codex отдаёт `thread_id`, opencode `sessionID`. Флаги codex стоят до `resume`. Продолжение, упавшее до работы (не лимит, не таймаут, без изменений), повторяется один раз с нуля (`meta.resume_failed`): флаги codex и opencode сверены с исходниками, а не с живым CLI.
- `config.example.yaml` равен `agent_dispatch/config_default.yaml` (есть тест).
