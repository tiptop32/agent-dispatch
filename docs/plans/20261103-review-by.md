# Ревью работы исполнителя другим исполнителем (`review_by`)

## Цель

Схема ролей владельца (2026-11-03): средние и мелкие задачи делает x5 (`omp/x5-code-large`), его
работу проверяет `omp/sol`, при проблемах задача уходит на sol по цепочке эскалации. Ревью
должно идти в демоне, а не в скиле вызывающего: тогда оно работает для любого клиента
(agterm, Orca, plan-dispatch), его нельзя забыть, и оно видно в `evals.replay`.

Измеримый результат: доля задач x5 с `review: fail`, доля из них, исправленных следующим
звеном, и цена ревью. Всё это видно в новой секции replay `post_review`.

## Поведение

1. У исполнителя появляется ключ конфига `review_by: <имя исполнителя>` (по умолчанию `null`).
   `Settings.validate_references` проверяет, что такой исполнитель есть и он не совпадает
   с самим исполнителем.
2. Демон запускает ревью сам, когда одновременно выполнено следующее:
   - задача на правку (`kind: task`, не `review`);
   - у исполнителя задан `review_by`;
   - после `verify` у результата статус `completed`. Упавшая проверка уже даёт `partial`
     и эскалацию, ревью тогда не нужно;
   - `changed_files` не пуст.
3. Место в `_run_executor` (`dispatch/dispatcher.py`): после `_verify` и до `_plan_escalation`.
   Работа к этому моменту ещё не интегрирована в рабочую копию вызывающего.
4. Ревью — обычная задача-потомок через `self.submit`, чтобы её было видно в `status`, в
   `tree_cost` для бюджета и в replay:
   - `kind="review"`, `executor=<review_by>`, `parent_task_id=<task_id>`,
     `hop=record.hop + 1`, `allow_escalation=False`, `source_agent` и `root_agent` как у задачи;
   - текст задачи — исходное задание исполнителя плюс одна строка о том, что проверяется
     работа другого исполнителя;
   - `cwd`: в режиме worktree это путь дерева, и перед ревью работа коммитится на ветку
     задачи (`worktree.commit`, повторный вызов возвращает HEAD). В режиме in_place это
     `req.cwd` вызывающего;
   - новое поле запроса `review_base: str | None`. Если оно задано, `build_task_package`
     для ревью берёт `git diff <review_base>` вместо `git diff HEAD`. В worktree демон
     ставит туда `tree.base`, иначе ревьюер не увидел бы закоммиченную работу.
     В шаблоне строка `$ git diff HEAD` показывает фактическую команду;
   - демон ждёт потомка (`self.wait(child_id, ...)`, срок равен таймауту ревьюера по
     `Settings.timeout_for`).
5. Вердикт. В блок результата (`schemas/agent_result.schema.json`, `ExecutionResult`,
   `result_parser`) добавляется необязательное поле `verdict: "pass" | "fail"`. Раздел
   «Review only» шаблона просит ставить `fail`, если до слияния что-то нужно исправить:
   ошибку, неверное поведение или отсутствующий тест на изменённое поведение. Иначе `pass`.
   Старые ревью без поля остаются валидными.
6. Итог пишется в `result.meta.review`:
   `{"by": <ревьюер>, "task_id": <id потомка>, "verdict": "pass"|"fail"|"unknown"|"skipped", "summary": <первые 2000 символов>, "reason": <для skipped>}`.
   - `skipped` — ревью не запустилось: guard отказал (периметр, глубина `max_hops`, бюджет),
     ревьюер недоступен или остывает, потомок упал или не уложился в срок. Работа
     не блокируется, в `reason` пишется причина;
   - `unknown` — ревью прошло, но вердикта в отчёте нет. Работа тоже не блокируется.
7. При `fail`:
   - `completed` превращается в `partial`, `error = "review failed (<ревьюер>)"`. Текст
     ревью в `error` не кладётся: `health.classify_failure` не должен принять слова
     ревьюера за лимит CLI;
   - `escalation.should_escalate` возвращает `review_failed`. Проверка идёт после
     `verification_failed` и до `tests_failed`;
   - дальше работает существующий механизм: работа удерживается (`integration_held`),
     следующее звено цепочки стартует с HEAD. Если цепочка исчерпана, результат становится
     `failed`, работа интегрируется, а ревью остаётся в `meta`;
   - следующее звено получает замечания: `_escalate` дописывает в `context` копии
     запроса блок «Review of the previous attempt by <ревьюер>: <summary>».
8. Ревьюер, сам заданный как исполнитель с `review_by`, ревью не получает: ревью
   идёт только у задач `kind: task`.
9. Периметр сильнее ревью. Если задача под корпоративным периметром, а ревьюер внешний,
   `_perimeter_refusal` откажет потомку, и в итоге будет `skipped` с причиной `perimeter`.
   Отдельной ветки для этого не нужно, нужен только тест.

## Видимость

- В компактном ответе MCP (`mcp/server.py`) добавляется строка
  `review: <verdict> by <ревьюер>`. Для `fail` в неё же идёт первая строка summary,
  для `skipped` — причина.
- В `evals/replay/harness.py` добавляется секция `post_review`: сколько ревью было и с каким
  вердиктом (`pass`, `fail`, `unknown`, `skipped` с причинами), сколько эскалаций
  `review_failed` и чем кончились их цепочки (`completed` или нет), суммарная цена ревью.
  Её выводит `render`, рекомендация появляется при `skipped` больше 20%.
- События: `review_by` при старте (`child`, `by`) и при итоге (`verdict`).

## Конфиг

- `ExecutorSettings.review_by: str | None = None`.
- В `config_default.yaml` и `config.example.yaml` (они обязаны совпадать, есть тест)
  добавляется закомментированная строка-пример у `omp/x5-code-large`:
  `# review_by: omp/sol`.
- Пользовательский конфиг владелец правит сам: `omp/x5-code-large: review_by: omp/sol`.

## Тесты (TDD, `tests/test_review_by.py`, фейки `tests/fakes/adapters.py`)

Образец настройки — `_make` из `tests/test_verify.py`. Поведение:

1. `completed` с изменениями → запускается ревью у `review_by` в режиме только чтения
   (`ctx.read_only`), у потомка `parent_task_id` и `kind: review`, `meta.review.verdict == "pass"`,
   эскалации нет.
2. `fail` → результат `partial`, причина эскалации `review_failed`, следующее звено цепочки
   запущено, в его `context` есть summary ревью.
3. В режиме worktree при `fail` работа удержана (`integration_held == "escalated"`), рабочая
   копия вызывающего не изменилась. Ревьюер получил `cwd` дерева, а пакет показал
   `git diff <base>` с изменениями исполнителя, в том числе новый файл.
4. Без `changed_files`, при упавшем `verify`, у исполнителя без `review_by` и у задачи
   `kind: review` ревью не запускается.
5. Вердикта нет → `unknown`, работа не блокируется.
6. Потомку отказал guard (`max_hops`) или ревьюер упал → `skipped` с причиной, работа
   не блокируется.
7. Цепочка исчерпана после `fail` → `failed`, работа интегрирована, `meta.review` на месте.
8. Конфиг: несуществующий `review_by` и `review_by` на себя дают ошибку загрузки.
9. `should_escalate` возвращает `review_failed` и соблюдает порядок с `verification_failed`
   и `tests_failed`.
10. Схема и парсер принимают `verdict`, отклоняют другие значения, старые отчёты без него
    парсятся.
11. `build_task_package` с `review_base` берёт `git diff <base>`.
12. MCP: строка `review: fail by omp/sol — …`.
13. Replay: `post_review` считает вердикты, причины `skipped` и исходы цепочек.

Каждый тест поведения должен падать на коде без изменения.
