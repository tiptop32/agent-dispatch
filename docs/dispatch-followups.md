# Dispatch followups: усвоенный рабочий цикл

Порядок работы, который сложился на задачах интеграционной гигиены AgentDispatch.
Он про то, как вести работу через `dispatch`, не затаптывая ни чужие правки в
общем дереве, ни своё незакоммиченное состояние.

1. **Заморозить критерии приёмки до работы.** Сформулировать финальное
   состояние — какие утверждения верны, какие тесты что проверяют, что считается
   ошибкой — и не двигать его по ходу. Правки в процессе подменяют цель.
2. **Изолировать независимых владельцев.** Разбить задачу на куски с
   непересекающимися списками файлов и раздавать каждый как отдельную
   подзадачу: правки одного исполнителя не должны зависеть от правок другого.
3. **Снять снимок грязного и пользовательского состояния.** До dispatch:
   `git status --short` (в том числе untracked и конфликтные пути индекса),
   что принадлежит пользователю (его CLAUDE.md, локальные конфиги). Эти файлы
   трогать нельзя, а список нужен, чтобы отличить свой результат от чужого.
4. **Сначала роутер, потом ручной выбор.** Обычная задача уходит через
   `dispatch` без указания исполнителя; `dispatch_to` — только с конкретной
   причиной выбрать исполнителя руками.
5. **Следовать за `task_id` и эскалациями.** Длинная задача возвращает
   `running` и id — опрашивать `status` по id, не пере-dispatchить ту же
   работу. Каждая эскалация создаёт новую задачу с новым `task_id`; исходный id
   остаётся рабочим хэндлом цепочки через `wait`/`status`, а
   `meta.escalated_to` указывает на следующую задачу.
6. **Зависимые правки — `workspace_mode: in_place`.** Worktree строится от
   HEAD и не видит незакоммиченного вывода предыдущего шага. Режим
   `workspace_mode` поддерживается в HTTP `DispatchRequest` и типизированном
   клиенте, но текущая MCP-сигнатура `dispatch` аргумента `workspace_mode` не
   имеет. Если правка опирается на ещё не закоммиченный результат другой
   задачи, используйте этот поддерживаемый API `in_place`, предварительно
   проверив владение файлами.
7. **Никогда не перезапускать активную работу.** Повторный dispatch той же
   задачи поверх работающего исполнителя кладёт второй результат на первый.
   Если статус потерялся — сперва `status` по id, потом решение.
8. **При сбое интеграции осмотреть сохранённый вывод.** Не применённый патч
   не выбрасывается: worktree и ветка остаются, путь и ветка лежат в
   `result.meta`. Забрать работу оттуда, а не гонять задачу заново.
9. **Мержить только свои пути.** Результат подзадачи принимается по дифу
   (`changed_files` из `git status`, не со слов исполнителя) и только по
   файлам из её списка; правки вне списка чужие или ошибочные.
10. **Фокусированные проверки, затем один общий gate и коммит у вызывающего.**
    Исполнитель гоняет только затронутые тесты; полный gate и коммит делает
    вызывающий, один раз, по всем принятым правкам вместе.
